## Findings and required follow-through

### Missing signing-state startup fallback

The original node startup recreated a zero H/R/S state when the state file was
missing despite an existing validator key. Strict `FilePv::load` already
returned an error, but startup bypassed it with `load_empty_state`. An isolated
API-level check confirmed that this discarded the signer's prior refusal state.

The revised startup uses strict loading and leaves a missing state absent.
The revised initialization applies the same rule: if either signing artifact
already exists, it requires the complete key/state pair to load. Only a pristine home with
neither artifact should receive initial zero signing state. In particular,
recovering a key from its mnemonic must not overwrite an existing sign state.
Retain regression tests for missing state at restart, repeated init with missing
state, and key-missing/state-present initialization. This is an operational
signing-safety finding, not an app-hash compatibility difference.

### Snapshot attempts must reconcile store sets

`App::offer_snapshot` originally unmounted fibre/valaddr for an offered v9
snapshot before checking the snapshot's format/metadata, and had no reverse
mount path for a subsequent v10 offer. A rejected offer could therefore change
the next attempt's mounted stores. `multistore::Restorer::start_store` rejects
unmounted stores, and `finish` requires every mounted store to be imported.

The correction rejects invalid offers without changing the mounted store set;
after a successful `begin_restore` it reconciles fibre/valaddr in both directions
for a fresh app before returning Accept. A later valid offer must replace a prior
failed/abandoned attempt independently. Keep tests for a rejected v9 offer
followed by v10, and an accepted then abandoned v9 attempt followed by v10.
This is a recovery-availability issue; source inspection did not establish an
app-hash split.

## Compatibility checks without an additional finding

- v10.5.0's Go multiplexer initializes its next version on startup and snapshot
  offers, and advances from committed app Info when consensus state lags an
  upgrade commit. Rust selects the executing version from committed consensus
  parameters when opening the app and mounts upgrade stores before handshake;
  it does not maintain the Go multiplexer binary-selection state. No additional
  binary-selection patch was identified by this source comparison. A persistent
  restart exactly after the upgrade commit remains necessary test evidence.
- The new cached ante helper discards store writes/events and restores the
  previous gas meter on rejection. The ante code inspected changes no other
  Context fields. ProcessProposal and v9 intentionally retain their prior
  semantics. Test rejected ante writes followed by a valid transaction, not
  just isolated invalid transactions.
- The upstream Hyperlane implementation records each ordered gas charge on
  the context meter and indexes those charges at each hop start. On a repeated
  ISM it takes the cycle slice, skips whole laps, and replays the final lap
  charge by charge, as Go v1.3.1 does. A successfully recorded lap fits u64 and
  includes at least the 10,000-gas verification charge, so its divisor is
  nonzero. Infinite meters and the finite `u64::MAX` limit use Go's routing-cycle
  error. Recording is cleared on terminal verification and ordinary error
  returns. Shipped routing handlers do not refund gas; future custom routing
  that refunds or changes state would need renewed comparison with Go's
  `gasRecorder.refunded` logic.
- Inspected the upstream Go-generated `hyperlane-routing.json` fixture and
  its Rust consumer. It includes 110 cases covering leaves, multi-hop paths,
  self/two/three-node cycles, a tail into a cycle, missing routes/ISMs, wrong
  types, finite gas boundaries, huge limits and infinite meters, with exact
  gas and failing-charge descriptors. The fixture is checked against the Go
  keeper by `routing_vectors_test.go`; this review did not rerun that generator.
- The current VerifyDryRun implementation rejects explicit limits over
  10,000,000 before decoding the other inputs, matching v10.5.0. The upstream
  implementation applies this bound regardless of the context's app version. Historical v9.0.8's
  Hyperlane query did not have this bound; a v9 query with a larger limit can
  therefore report a different error. This is a historical query compatibility
  gap, not a v10.5 mainnet consensus discrepancy. Version-gate the query cap or
  explicitly exclude that historical query behavior from the compatibility
  claim. The v10 cycle implementation is also used for v9 execution; finite
  routing is intended to preserve gas, but this review did not verify every
  historical v1.1.0 edge case against its oracle.

## Dependency advisory: RUSTSEC-2026-0387

Read-only follow-up checked the RustSec advisory, locked normal dependency
paths, production call sites, and crates.io dependency metadata. The advisory
covers compiler/CPU-dependent timing in integer operations intended to be
constant time; its patched range is `crypto-bigint >=0.7.6`. This is not an
assertion of a practical attack on this node.

- `Cargo.lock` has crypto-bigint 0.5.5 through elliptic-curve 0.13.8 and
  k256 0.13.4 / p256 0.13.2. This is a normal node dependency, not confined
  to tests. Do not classify the entire advisory as unreachable.
- Secret-scalar use is present in `keyring/src/hd.rs::derive_from_seed`, called
  by `Keyring::add_mnemonic` for account creation/recovery. It parses parent
  and HMAC-derived secret scalars and adds them modulo the secp256k1 order.
  k256's `Scalar::add` invokes crypto-bigint `Uint::add_mod`, whose reduction
  uses subtraction (`sbb`). Thus affected integer arithmetic is reachable
  on private derivation intermediates. This is local mnemonic/key creation,
  not the peer-facing consensus signing loop; exploitability was not tested.
- Production Hyperlane uses k256 to recover public keys from public message
  digests/signatures. The ante handler and tx decoder use p256 for public-key
  parsing and signature verification. Those inspected operations have no
  application secret scalar to disclose. k256/p256 signing in fuzz-diff and
  test modules generates test data, not production validator signatures.
- Production account transaction signing uses the existing libsecp256k1-backed
  `crypto::secp256k1::sign`; consensus vote/proposal signing uses
  `crypto::ed25519::sign`. Neither operation uses crypto-bigint on this path.

A lockfile-only update cannot fix this graph: elliptic-curve 0.13.8 requires
crypto-bigint `^0.5`. Current stable migration candidates are k256/p256 0.14.0
with elliptic-curve 0.14.2 (`crypto-bigint ^0.7.7`), ecdsa 0.17, signature 3,
and digest/sha2 0.11. Their minimum Rust version is at most 1.87, within this
workspace's 1.88 floor, but the API/type changes need coordinated updates in
keyring, Hyperlane, ante, txdecode, fuzz-diff and crypto's test-only reference.
Rerun BIP-32/Go keyring vectors, P256 and Ethereum recovery Go differentials,
and the application/replay checks before claiming equivalent behavior.

A narrower alternative can first move BIP-32 scalar addition onto the existing
libsecp256k1 backend, retaining the same derivation vectors. That removes the
identified production secret-arithmetic path but does **not** remove the
advisory or make the dependency audit pass: public verification still carries
the old dependency until the graph is migrated. No advisory suppression or
dependency modification was made in this review.

### Fee arithmetic panic semantics (open at discovery)

Go `app/ante/fee.go:76-79` computes priority, then calls `fee.Int64()` for
telemetry **before** fee deduction. `math.Int.Int64` panics with
`Int64() out of bound` when the fee does not fit int64. Rust
`x/ante/src/fee.rs::validate_tx_fee` originally omitted that conversion and
continued to fee deduction. This can change the tx error code/gas even when
the fee could never be paid; insufficient balance does not make the earlier
validation branch unreachable.

Also, Rust `get_tx_priority` originally returned zero when multiplying the
fee by 1,000,000 overflowed the bounded Int. Go's `math.Int.Mul` panics with
`integer overflow`; returning zero is only correct for an otherwise-computed
priority outside int64 (or zero gas). Preserve this order and model the two
panics through the existing ante recovery machinery. Add Go-generated cases
for int64 and 256-bit multiplication boundaries, covering code and gas as
well as error text. This finding is based on source comparison; no attack
or exploit demonstration was performed.

### IBC block-delay error detail (open at discovery)

Rust `lightclients/tendermint.rs::verify_delay_period_passed` originally
returned `cannot verify packet until height` on a block-delay failure.
Pinned Go `07-tendermint/client_state.go:325` additionally formats the valid
and current heights: `cannot verify packet until height: <valid>, current
height: <current>`. The code and gas appear equivalent, but the returned
text differs. Error text can be persisted as a governance proposal's failed
reason, so it should be compared rather than globally dismissed as logging.
Retain a regression with a nonzero block delay and a current height below
the valid height.

### No additional finding in the inspected cache/proof structure

The inspected packet paths write TAO verification only on success, discard
no-op/error branches, separately cache receive callbacks, discard unsuccessful
acknowledgement application writes while retaining converted error events,
and rely on the outer message runner to discard all message layers on a
returned error or recovered panic. The redundant-relay receive path skips
application callbacks as Go does. Proof bytes are decoded with the gogoproto
normalizer before Rust ICS-23 verification; membership checks retain Go's
height/delay/decode/consensus-state ordering.

These are source-review observations, not exhaustive handler or proof-library
certification. Valid proofs across every middleware path, rare client states,
all signature modes, and the remaining handlers still need their own review
and differential evidence. This additional scope does not close all of F1.12.

### Historical decoder version scope across worker threads (open at discovery)

`txdecode::default_tx_decode_v9` originally called
`with_v9(|| default_tx_decode(tx_bytes))`. For inputs over 8,192 bytes,
`default_tx_decode` moves decoding onto a large-stack worker thread. The V9
flag is thread-local and was set on the caller rather than that worker, so
that entrypoint used the v10 registry/schema for larger historical inputs.
The app's `query_services.rs` selects this entrypoint for historical TxDecode
queries. The main `decode_v9` entrypoint already places `with_v9` inside its
worker closure correctly.

Use that same nesting for the default decoder and retain a length-boundary
regression proving that a v10-only message is rejected at v9 regardless of
which thread performs decoding. This is a historical query/decoder semantic
finding; no exploit demonstration was performed.

### Authz NewCoins panic detail (open at discovery)

`authorization.rs::new_coins` originally returned the generic panic text
`invalid coins` when a sanitized MsgSend amount was invalid. Go SDK
`types/coin.go::NewCoins` returns `invalid coin set <sanitized coins>:
<Coins.Validate error>`. SendAuthorization.Accept invokes this before the bank
handler, and SDK0.52.12's MsgSend does not implement HasValidateBasic, so the
branch is reachable through Exec. Match the precise sanitized coin and
validation error text. Recovered panic text may become governance failure
state for proposals that execute such an authorization path.

### Feegrant SafeSub preprocessing (open at discovery)

`feegrant/allowance.rs::safe_sub` originally negated the supplied fee directly
and used the Rust pairwise `Coins::add` merge. Go `Coins.SafeSub` first calls
`NewCoins` on the subtrahend: it sorts/removes zero coins and panics on duplicate
or invalid denominations. Positive duplicate fee entries are not rejected by
Tx.ValidateBasic, which only checks nil/negative fee amounts. They can therefore
reach Basic/Periodic allowance acceptance. Go's invalid-coin-set panic and
Rust's fee-limit-exceeded response have different tx codes/gas. Compare this
boundary using Go-generated ante/allowance cases; reuse the precise NewCoins
semantics rather than merely changing the panic string in authz.

### Circuit address-codec mismatch (open at discovery)

Circuit message handlers originally called `sdk::address::acc_from_bech32`,
while Go's circuit keeper is wired to the account address codec and calls
`StringToBytes`. A wrong-prefix grantee in AuthorizeCircuitBreaker reaches the
handler without being a transaction signer: Go reports sdk/35 (HRP mismatch),
while Rust reports undefined/1 (invalid Bech32 prefix). Use the account codec
for the handler's granter/grantee/authority fields; compare genesis handling
against its own Go entrypoint separately.

### Valaddr host length after Go-form conversion (open at discovery)

`ValidateHost` uses `gostr::go_len`, but the SetFibreProviderInfo handler
originally used Rust `m.host.len()`. Valid U+10FFFF is escaped in the internal
Go-form string, so its internal Rust length can exceed the original Go byte
length. A host within Go's MaxHostLen can pass basic validation and then be
rejected only by Rust's handler. Use Go byte length for both the handler check
and its reported length; include valid Unicode sentinel and ASCII boundaries.
This finding does not depend on accepting invalid UTF-8.

No exploit demonstrations were performed. These are source-level findings
requiring candidate regression results before closure. The module coverage
above remains selective, and does not close the remaining F1.12 requirements.

## Staking, distribution and slashing follow-up

The independent reviewer inspected the exact rc.3 commit
`6ef37deb17f49fc5d8bef777aba5588331f87f9c` read-only against celestia-app
v10.5.0 / cosmos-sdk v0.52.12, checking staking message handlers and
delegation/slashing flows, distribution handlers/hooks, and slashing
parameter/signature/unjail paths. The v9.0.8 SDK has the same parameter
validation rules.

Three state-transition findings invalidated rc.3 as a release candidate.
Staking's minimum commission rate, slashing's minimum signing and slash
fractions, and distribution's community tax are nil in Go when their wire
fields are omitted. Go rejects those nil values. Rust's `LegacyDec` does not
model nil and the handlers accepted each omission as an explicit zero. A
passed governance proposal could therefore fail on Go while updating stored
parameters on Rust. The replacement candidate retains the raw wire fields
through validation, distinguishes omission from explicit zero, and checks in
Go's order. Focused tests cover nil, zero and earlier-error ordering; the
governance-passing differential generator now constructs all three omissions.

The same batch found a smaller staking error-detail mismatch: Go formats the
allowed consensus-key types with `%s` on a string slice (`[ed25519]`), while
Rust used Debug (`["ed25519"]`). This can enter a failed governance proposal's
stored reason and is corrected with Go slice formatting.

No additional actionable mismatch was identified in the other inspected
paths. This batch did not exhaust every store helper, migration, genesis or
end-block boundary, so it extends but does not complete F1.12.
