# Operator sync comparison

The Go reference is [celestia-app v11.0.0](https://github.com/celestiaorg/celestia-app/releases/tag/v11.0.0), commit `58be8ae90d00518800df5506b3a1e988f009c1c6`. Record the Rust commit and both executable checksums. The [2026-11-25 runs](operator-sync-2026-11-25.md) are the first v11 cloud measurements. The [2026-11-26 runs](operator-sync-2026-11-26.md) validate the old-snapshot fix and compare the DA stacks over an equal retained range and matching client reads. The [October Mac Mini measurements](replay-and-node-benchmarks.md#results-mac-mini-m4-2026-10-20-b1-reference) remain a separate v10.4.0 series.

## What to time

Run non-validating consensus full nodes with DA bridge services disabled on both sides. Use the same chain ID, verified genesis digest, peer set, pruning and transaction indexing policy. Include any historical binaries and upgrade restarts needed for genesis replay. Verify that archive peers actually serve height 1 through the target and that each implementation supports those historical versions. A missing interval or unsupported upgrade is a recorded failure.

| Starting point | Start the timer | Finish |
| --- | --- | --- |
| State sync | First process launch with empty data, identical trust inputs, snapshot height and providers | First verified tip |
| Genesis prefix | First process launch with verified mainnet genesis installed and empty data | Execution of a fixed height H, verified against the app hash in signed header H+1 |

Provision identical dedicated Linux VMs and empty data disks in the same zone. Start the pair together. Record the machine and disk types, vCPU count, RAM, disk capacity, OS, network, software and configuration. Keep providers outside the measured VMs. Record actual snapshot height, restore completion and first post-restore commit separately. Discard a paired comparison if different snapshots were restored.

Poll local and independent reference RPCs every five seconds. Record monotonic elapsed time, local height, reference height and catching-up state. Count a node as at tip when catching_up is false and it is within one block of the reference on two consecutive polls with advancing local heights. Verify the chain ID and local block ID against the reference at the common height. Use the first qualifying poll as finish time after confirmation. Also record time to a common fixed checkpoint for pairs whose live tips differ. Timeouts, divergent hashes and interrupted runs get the last verified height and reason. Do not extrapolate a finish time.

## Mainnet prefix and optimization trials

Start with H = 10, the height covered by the retained v1 conformance window. On 2026-11-24 a local preflight with the v0.1.0-rc.9 Linux release and the canonical mainnet genesis (SHA-256 `9727aac9bbfb021ce7fc695a92f901986421283a891b89e0af97bc9fad187793`) stopped at InitChain with `gov genesis params are nil`. The genesis has separate deposit, voting and tally parameters. No block executed. On 2026-11-25 the node learned to read the genesis app version 1 and to store these gov parameters as cosmos-sdk v0.46 does. InitChain now stops later, at IBC: `invalid ibc channel genesis state parameters: upgrade timeout timestamp invalid: 0: upgrade timeout is invalid`. Later on 2026-11-25 the node gained an app version 1 state machine (a cosmos-sdk v0.46 driver with the v1 store set). The [historical replay test](../../conformance/README.md#historical-mainnet-replay) then executed heights 1 to 10 from this genesis and matched every app hash. A transaction that reaches a v1 behavior that is not ported yet stops the node with an error naming the height and the transaction.

Require historical initialization and matching commitments before timing this prefix. Extend H only after a successful run; hold H and inputs constant across optimization trials. Time initialization and subsequent block execution separately. Profile baseline CPU, storage I/O and peer wait time before changing the implementation. Compare the baseline and candidate on fresh volumes with identical verification enabled and report repeated durations and hash checks. A later checkpoint is a separate series with its own start height.

For cloud trials, preprice both machines, disks, IPs and network charges together. Bound runtime and traffic, use disposable auto-deleted disks, and include cleanup headroom within the $10 ceiling for each comparison. A billing alert alone cannot enforce that ceiling.

## Resources and reporting

- Place the node and its child processes in a dedicated cgroup v2 service. Report peak cgroup memory (includes charged file cache), sampled process-tree RSS with its sampling interval, and steady-state memory after 30 minutes at tip. Preserve the cgroup peak before stopping the service, including across any upgrade restarts.
- Use an empty, dedicated data filesystem. Report allocated bytes for the whole node home, block store, application state and snapshots. Sample filesystem used bytes during sync for a high-water mark. Report the initial baseline and retained height range. For an equal-height comparison, use a matched checkpoint run stopped gracefully at the same height and take the disk measurements after shutdown.
- Record elapsed times, peak RAM, steady-state RAM, peak disk and final allocated bytes in original units for each implementation and trial. Keep raw timestamped measurements, configuration, peer IDs and the verification receipt. Run three cold pairs if the budget allows, publishing each pair and the median. Label a single pair as one observation. Record failed attempts alongside completed runs.
- Benchmark the integrated DA bridge separately against the Go consensus-plus-bridge stack, with matching DA retention and client workload. Consensus-only measurements do not quantify the resource cost of serving DA.

## Running the campaigns

[`operator-benchmark.yml`](../../.github/workflows/operator-benchmark.yml) runs these comparisons without SSH. Dispatch it from `main`. `provision` creates every pair in one call: two identical `n2-standard-8` VMs with an empty 200 GB `pd-balanced` data disk each, in `us-central1-a`. Each VM deletes itself at its maximum run duration. Each VM runs [`scripts/bench/vm.sh`](../../scripts/bench/vm.sh) from its startup script. It builds its executable outside the timed interval: celestia-rs from `rust_commit` with `--features da-light`, or celestia-app `v11.0.0` with `make build` (multiplexer). Then it starts one node as a transient systemd service in `benchnode.slice` and polls it. Both sides get the same genesis, seeds, peers, trust inputs, pruning (`custom`, 100 versions, interval 10, 3000 retained blocks), snapshots off and no transaction index. The VMs use Standard Tier networking and cap egress at 4 Mbit/s.

| Campaign | Dispatch inputs | VM lifetime | Worst-case price |
| --- | --- | --- | --- |
| Genesis prefix | `action=provision campaign=genesis-prefix height=10` and, if needed, archive `peers` | 3 h | $3.51 |
| State sync | `action=provision campaign=state-sync pairs=1` (up to 3 concurrent cold pairs) | 4 h | $4.68 per pair |
| DA bridge | `action=provision campaign=bridge pairs=1` | 3 h | $3.51 per pair |

| Block range | `bash scripts/bench/cloud.sh provision` (local dispatcher, below) | 4 h | $11.84 per pair (`n2-highcpu-32`, 4 local SSDs) |

`rust_commit` defaults to the dispatching commit. Extend `height` only after a successful run. The workflow's header comment has the price arithmetic. The job summary prints the run ID and the deletion time.

Genesis prefix polls every second until the local height reaches H. It waits for H+1, then compares the local header H+1 app hash with the reference RPC and runs `packaging/check-apphash.sh`. CometBFT serves RPC only after its ABCI handshake, so `rpc_up_s` includes InitChain on Go. `first_height_s` and `target_s` bound block execution at poll resolution. State sync polls every five seconds until the tip rule above holds. It then checks the chain ID and block ID at the local height and stays at tip for 30 minutes. A stopped service, no height change (30 minutes for genesis prefix, 60 for state sync) or the deadline ends the run with the last height and a reason.

Both bridge-campaign VMs first sync consensus with DA disabled and verify the tip against mainnet. celestia-rs then restarts with its integrated bridge. The Go VM starts celestia-node `v0.36.0` (commit `d5dfb21a0885622828e30e8e2daf50e5d1bb72b2`) in the consensus service’s cgroup slice. On a fresh index Rust starts at the oldest locally retained consensus block. The runner sets Go’s `[Header.Syncer].SyncFromHeight` to its local consensus base before starting the bridge. Both bridges keep their normal time-based DA retention.

Provisioning fixes the same future mainnet height H for every VM, about 90 minutes ahead using the previous 100 block timestamps. Each bridge must report its expected tail and a local head of exactly H at entry and H+600 at exit. At both boundaries Go must also report a contiguous sampled chain through the local head with zero failed heights. The client reads share (0,0) at the tail, H, and every 20 blocks through H+600. It records the 32 heights and returned shares in `da-reads.tsv`. A valid pair has matching snapshots, verified tips, the same observed DA bounds and matching SHA-256 receipts. Missing the scheduled block, losing the tail, and failed reads disqualify a run. Uncontrolled public peer traffic can still differ.

`da-memory.tsv` measures the 600-block window independently of the initial state sync. It records cgroup current bytes, process-tree RSS in KiB, cumulative CPU microseconds, anonymous and file bytes, and filesystem usage at both endpoints and approximately every five seconds. The pre-DA snapshot-to-tip memory figures are in `sync_peak_B` and `sync_tip_rss_KiB`. Use the maximum of those samples for window memory and subtract endpoint CPU counters for window CPU time. `slice_peak` covers the full process lifetime, including both Rust services across the restart. Compare DA-client figures only for pairs with a `valid` bridge verdict.

The block-range campaign is the consensus-only equal-height comparison. Provisioning fixes a future height H (`--lead-min`, default 60 minutes ahead) and a block count N (`--blocks`, default 1000) for every VM. Each node state-syncs and verifies its tip as above, and must be at tip before H; a node that is not is a failure (`missed_range_start`). Both sides set `halt-height = H+N+1` (celestia-rs also gets `--halt-height`), so each stops before executing H+N+1. From the first poll at or above H to the first at or above H+N, polls run every 5 s (1 s within three blocks of either boundary) and `range-memory.tsv` samples cgroup memory, process-tree RSS, CPU and filesystem use. The runner then waits up to 3 minutes for the halt, records the last committed height from `/abci_info`, stops the service and measures `du` and filesystem use after shutdown. A node that does not halt is stopped anyway with its actual height. The summary `range` object holds the window statistics, retained heights and end state; `host` records the machine, CPU flags and data disk layout. A pair is `valid` only with matching snapshots, the same schedule and the same final committed height; otherwise the verdict names the gap, for example `discard:different_final_heights:rs=…,go=…,diff=…`.

[`scripts/bench/cloud.sh`](../../scripts/bench/cloud.sh) creates the same VMs with local `gcloud` credentials: `provision` (prints an upper-bound price and refuses above `--max-usd`, default $40), `status`, `collect` and `delete`, each with `--dry-run`. It defaults to `n2-highcpu-32` (Ice Lake or newer) with 4 local NVMe SSDs striped as RAID 0; `--data-disk-gb` and `--data-disk-type` select a persistent disk instead. Resources carry `owner=claude-blog-bench` and `bench-run=<run-id>` labels, and `status` and `delete` match only both. [`scripts/bench/report.py`](../../scripts/bench/report.py) turns a `collect` directory into a table of time to tip, range peak memory and node home size per valid pair, with medians.

Each VM stops its node, preserving the cgroup peak first, and publishes guest attributes under `bench/`: `status`, `summary` (JSON) and `raw-0`… (compressed polls, logs, configuration and `du` per data directory). Dispatch `action=collect` with the same `campaign`, `pairs` and `run_id` before the deletion time. Its job summary shows each VM's status; if one does not read `done-…` yet, dispatch it again later. The artifact `operator-bench-<campaign>-<run_id>` keeps the results for 90 days and lists pair validity. A pair that restored different snapshots is `discard:different_snapshots`. Then dispatch `action=delete` to stop charges early. Record each run, including failures, in a dated `docs/benchmarks/operator-sync-<date>.md` with its run ID and artifact. Do not add it to this protocol.
